# 최고 관리자 페이지 — 무엇이 있어야 하는가 (분석 · 2026-07-30)

## 결론

**`/admin` 라우트는 존재하지 않는다.** 관리자(`profiles.role='admin'`, 현재 5개 계정)가 가진 기능은
세 가지뿐이고 **전부 본인 테스트용**이다 — 남의 것은 하나도 못 건드린다.

| 지금 관리자가 할 수 있는 것 | 코드 | 한계 |
|---|---|---|
| 병원·간호사 화면으로 보기 전환 | `mypage/actions.ts` `setViewAs` | 12시간 쿠키. 화면만 바뀜 |
| 결제 없이 광고 적용 | `mypage/ads/actions.ts` `activateAdFree` | `ownedJobHospital(...)` 로 **자기 소유 공고만**. 남의 병원엔 못 씀 |
| 전용 테스트 병원 생성 | `mypage/actions.ts` `adminTestHospitalId` | 실제 명부 침범 방지용 |

RLS 쪽도 마찬가지다. `is_admin()` 은 **커뮤니티(리뷰·게시판)에만** 걸려 있고,
그 안에서도 삭제 정책이 `author_id = auth.uid()` 를 유지해 **관리자도 자기 글만 지운다.**
`jobs` · `ad_orders` · `profiles` · `hospitals` · `resumes` 의 RLS 에는 `is_admin()` 이 **아예 없다.**

즉 이번 세션에서 이력서 298건을 숨기고, 오염된 본문을 고치고, 오분류를 정리한 일은
**전부 Supabase 콘솔에서 SQL 로만 가능했다.** 오픈 후에도 같은 일이 생기면 같은 방법뿐이다.

## 1순위 — 오픈하는 순간 손이 묶이는 곳

### 1-A. 결제 사고 처리 (지금 처리 경로가 0이다)

포트원 연동은 되어 있고 키만 넣으면 돈이 돌기 시작한다. 그런데:

| 사고 | 지금 벌어지는 일 | 코드 근거 |
|---|---|---|
| 손님이 결제창을 닫음 | 클라가 문구만 띄우고 **서버에 안 알린다**. 주문이 `PREPARE` 로 **영구히 남는다** | `AdPurchase.tsx:40` |
| 결제액 ≠ 주문액 | 주문 상태를 **안 바꾼다**. 돈이 나갔어도 아무도 모른다 | `actions.ts:1010` |
| 포트원 콘솔에서 취소 | **우리 DB 는 모른다.** `PAID` 그대로, 광고도 계속 나간다 | `iamportWebhook` 이 `paid` 아니면 `ignored` |
| `FAILED` 로 찍힌 주문 | 후처리 없음. 재시도 버튼도 조회 화면도 없다 | — |
| 광고 살아있는 공고를 삭제 | 그냥 지워진다. 주문은 남지만 어느 공고였는지 잃는다 | `job_id on delete set null` |

화면이 손님에게 하는 안내는 **"결제가 되었다면 고객센터로 문의해 주세요"** 한 줄인데,
그 메일을 받은 사람이 **앱 안에서 고칠 수 있는 화면이 없다.**

**필요한 것**
- 전체 주문 조회 (병원·기간·상태·금액으로 검색). 지금은 RLS 상 본인 주문만 보인다
- 주문 상태 수동 전환: `PREPARE` 정리, `FAILED` 재시도, **`CANCELED`** (DB check 에는 있는데 쓰는 코드가 0건)
- 남의 병원 공고에 광고 **수동 부여·연장·회수** (사고 보상용). 지금은 `activateAdFree` 가 자기 공고만
- 포트원 거래 조회 붙이기 — `imp_uid` 로 실제 결제 상태를 화면에서 대조
- 매출 집계: 기간별 합계, `tier='admin_test'`(금액 0) 제외 규약은 이미 있다
- 환불은 안 하기로 확정했지만(약관 제9조), **취소 기록**은 남길 수 있어야 한다

### 1-B. 병원 인증 분쟁 (사이트가 이미 약속해 놓고 지킬 코드가 없다)

사업자 인증은 **국세청 API 로 완전 자동**이라 승인 대기열은 필요 없다. 문제는 그 다음이다.

지금 `/mypage/verify` 화면이 손님에게 하는 말:
> "이미 다른 계정이 등록·관리 중인 병원입니다. 고객센터로 사업자등록증과 함께 알려주세요 —
> **확인 후 연결을 옮겨드립니다**"

**옮기는 코드가 없다.** 공고가 있는 병원도 마찬가지("공고를 유지한 채 옮기려면 고객센터로").
병원 하나를 두고 두 계정이 다투면 지금은 해결 수단이 없다.

**필요한 것**
- 병원 ↔ 계정 연결 강제 이전 / 해제 (공고를 유지한 채)
- 사업자 인증 수동 부여·취소 (국세청 API 가 죽었을 때, 정당한데 통과 못 한 병원)
- 79,898건 명부 검색 + 병원 정보 정정 (HIRA 데이터가 틀린 경우)

### 1-C. 신고와 제재 (테이블도 버튼도 없다)

- `reviews` 에 **`is_hidden` · `report_count` 컬럼이 이미 있는데 값을 쓰는 코드가 0건**이다.
  신고 버튼도, 숨김 처리도 없다. 죽은 컬럼이다
- 게시글·댓글 6,528건에 대해 **관리자도 남의 글을 못 지운다**
- 회원 정지·차단 기능이 없다. `jobs.status` 에 `'hidden'` 값이 DB check 에는 있으나 **설정하는 코드가 없다**
- 신고 접수 테이블이 없다

**필요한 것**
- 신고 접수(무엇을·누가·왜) → 처리 대기열 → 조치(숨김/삭제/경고/정지) → 결과 기록
- 관리자 강제 삭제·숨김: 리뷰 · 게시글 · 댓글 · 공고 · 이력서
- 회원 정지(기간제) / 영구 차단
- **RLS 를 고쳐야 한다** — 지금은 관리자에게 남의 것을 지울 권한이 DB 레벨에 없다

## 2순위 — 매일 하는 운영

### 2-A. 회원

16,273명(간호사 13,606 · 병원 2,662 · 관리자 5). 지금 화면에서 **한 명도 조회할 수 없다.**

- 검색(이름·이메일·아이디·전화·가입일·역할), 상세 보기
- 이력서 강제 비공개 — 이번에 298건을 SQL 로 했다. 다음에도 SQL 이다
- 개인정보 열람·삭제 요청 대응 (법정 의무. 지금은 SQL 뿐)
- 대리 탈퇴 처리
- **관리자 임명** — `role='admin'` 을 부여하는 코드가 전 소스에 없다. DB 직접 수정만 가능하다

### 2-B. 공고

- 관리자가 임의 공고를 내리거나 고칠 수 없다 (병원 본인만)
- 워크넷 오분류를 화면에서 못 고친다 — 지금까지 전부 SQL 마이그레이션이었다
  (`fix_specialty_false_positives`, `specialty_cleanup_guards`, `specialty_recleanup`, `specialty_recover_busicont`)
- 개별 공고의 진료과·시설유형 수정, 강제 마감·숨김, 스팸 일괄 처리

### 2-C. 사이트 콘텐츠

공지사항·FAQ·이벤트가 **TypeScript 파일**(`src/lib/customerContent.ts`)에 있다.
문구 한 줄 바꾸려면 코드 수정 + 재배포다. 오너가 혼자 못 한다.

- 공지 작성·수정·삭제 (테이블 + 작성 화면을 **같이** 만들어야 의미가 있다)
- FAQ · 이벤트 편집
- 광고 상품·요금 편집 (`src/lib/adPlans.ts` 도 지금은 코드다)

## 3순위 — 사고를 미리 아는 것

크론 3종이 **실패해도 아무도 모른다.** DB 에 실행 기록을 남기는 코드가 없고,
`sync-worknet` 은 `console.error` 조차 호출하지 않는다.

| 크론 | 주기 | 실패하면 |
|---|---|---|
| `sync-worknet` | 하루 4회 | 공고가 갱신 안 됨. **조용하다** |
| `sync-hospitals` | 주 1회 | 명부가 낡음. **조용하다** |
| `guard-avatars-bucket` | 10분 | **증명사진 버킷이 공개로 열려도 못 막는다.** 코드 주석이 스스로 인정: "이 라우트가 계속 실패해도 조용하다" |

**필요한 것**
- 크론 실행 기록 테이블 + 마지막 성공 시각·처리 건수·실패 사유
- 화면에서 수동 재실행 (지금은 `CRON_SECRET` 을 알고 curl 을 쳐야 한다)
- 실패 알림 (SMTP 붙은 뒤)
- 대시보드: 가입·공고·지원·매출 추이, 대기 중인 신고·주문

## 만들 때 반드시 같이 가야 하는 것

1. **감사 로그** — 관리자가 남의 데이터를 고칠 수 있게 되는 순간, 누가 언제 무엇을 왜 바꿨는지
   남지 않으면 사고가 나도 추적이 안 된다. 관리자 5명이 서로를 확인할 방법도 없다.
   지금 감사 로그 테이블은 없다.

2. **권한 모델 결정** — 두 갈래다.
   - (a) RLS 에 `is_admin()` 을 추가한다 → DB 가 지켜주지만 정책을 여러 테이블에 손대야 한다
   - (b) 관리자 화면만 `createAdminClient`(service_role, RLS 우회)로 돈다 → 빠르지만
     **`/admin` 의 접근 검사 한 줄이 뚫리면 전부 뚫린다**
   지금 결제·인증이 (b)로 돌고 있고, `admin.ts` 주석이 "사용자가 넘긴 id 를 그대로 조회하는 데
   쓰면 안 된다"고 못박아 뒀다. 관리자 화면은 그 규칙을 정면으로 어기는 용도라 **별도 판단이 필요하다.**

3. **관리자 인증 강화** — 지금 관리자는 일반 로그인과 똑같다. 비밀번호 하나가 뚫리면
   16,273명의 개인정보에 닿는다. 2단계 인증이나 최소한 재인증(민감 작업 전 비밀번호 재확인)이 필요하다.

## 규모 감

| 묶음 | 내용 | 크기 |
|---|---|---|
| 0. 뼈대 | `/admin` 라우트 + 접근 검사 + 레이아웃 + 감사 로그 테이블 | 작음 (먼저 해야 함) |
| 1. 결제·주문 | 주문 조회/상태 전환/광고 수동 부여·회수/매출 | 중간 |
| 2. 회원·병원 | 검색·상세·제재·연결 이전·인증 수동 처리 | 중간 |
| 3. 신고·모더레이션 | 신고 테이블 + 대기열 + 강제 삭제/숨김 + **RLS 개정** | 중간~큼 |
| 4. 콘텐츠 | 공지·FAQ·이벤트·상품요금 편집 (테이블 이관 포함) | 작음~중간 |
| 5. 관측 | 크론 로그·대시보드·알림 | 작음 |

**권하는 순서**: 0 → 1 → 2 → 3 → 4 → 5.
0 없이는 나머지를 못 얹고, 오픈과 동시에 돈이 도니 1이 급하다.
3은 RLS 를 건드려야 해서 가장 조심스럽다.
